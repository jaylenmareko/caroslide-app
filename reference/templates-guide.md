# Template library

Eleven proven layouts in `templates/`, plus `cta.html` (always the last slide, every carousel, unflipped). Rotate by default — check the project's carousel log for the last template used and don't repeat it back-to-back. Only design a new layout when the user explicitly asks for something structurally different; if you do, save it into `templates/` as `12-whatever.html` with the same scaling-note-comment convention so the library actually grows.

**A themed "circles bleed off the side edges" variant (was briefly `11-circles-bleed.html`) was tried and removed 2026-07-18.** The reference it was based on shows the subject's own body physically overlapping in front of the circles (a foreground cutout composited over the circle layer) — that occlusion effect can't be reproduced for an arbitrary rectangular `BG_IMG` the way every template in this library needs to work with any photo, not a pre-cut transparent subject. Circle position was also wrong on the first attempt and needed a correction before removal. If a real cutout-compositing template is wanted in the future, it needs a different content-sourcing requirement (a pre-cut subject photo, not just any photo) — flag that explicitly before building it, don't repeat the same approach. The freed-up `11-` slot was later reused by a genuinely different design — see #11 below — not a resurrection of Corner Bleed.

**#2, #6, #8, #9, and #11 are dual-mode (#6 and #11 are triple-mode), same pattern as #4:** each carries multiple mutually-exclusive content pairs in the same zone at once — fill whichever set fits the slide and leave the others' placeholders unset (`fill_template.py` renders an unset placeholder as an empty string via its `|` default, so unused sets just don't render). There is no separate `-stat.html` file for any of them — "stat mirror" means filling `STAT_NUMBER`/`STAT_LABEL` instead of the plain-caption placeholders on the exact same template file, not a second HTML file. #2 (`.caption` vs `.stat`/`.statlbl`), #8/#9 (`.tagline`/`.caption` vs `.stat`/`.statlbl`), #6/#11 (`.kicker`/`.headline` for cover slides, `.story` for narrative slides, or `.stat`/`.statlbl` for a stat takeover — three mutually-exclusive sets, exactly one filled per slide).

**#2 and #6's stat mode were added 2026-07-18, after shipping with a real bug:** both templates originally had no dedicated `.stat` class at all — "stat mode" meant just writing the number as the first word of the normal-size caption/headline text (70px on #2, 56px on #6), which reads as barely-bigger than the surrounding sentence, not as a dominant stat callout. Compare to #4's 165px or #8/#9's 120px `.stat` — that's the size a number needs to actually read as *the* stat, not a stat mentioned in passing. If a future template needs a stat mode, give it a real oversized `.stat` class from the start; don't fold the number into existing body-text-sized markup.

**#10 deliberately has no stat mirror.** A giant stat number overlaid on a busy photo split via just a gradient scrim risks poor legibility depending on what's under it. If a stat is needed with a similar 2-photo-split feel, use #9's stat mode instead — it puts the number on a solid black zone where legibility is guaranteed.

**#11's circle size/position was measured pixel-for-pixel off a real reference (2026-07-19), not guessed.** A news-style screenshot (IMG_3583, KTLA breaking-news graphic) showed the exact look wanted: a large single circle inset, close to the top-right corner. Measured the reference at its native 1320x1640 (circle spans x:785-1285, y:195-690 — a ~500px circle, 35px off the right edge, 195px off the top) and scaled by width ratio (1080/1320 = 0.818, applied uniformly to both axes so the circle stays a true circle) to get the template's starting defaults: `CIRCLE_SIZE: 410px`, `CIRCLE_TOP: 160px`, offset 29px off the edge. Confirmed matching within a fraction of a percent after rendering a real test slide — when matching a specific reference image's geometry, measure the actual pixel coordinates rather than eyeballing a plausible-looking size. The exact-match offset was then nudged twice per direct feedback (29px → 60px → 120px, current `CIRCLE_OFFSET` default) — the tight edge-hug that matched the reference exactly read as cramped against other real photos.

**#11 mirrors left/right the same way #4 does.** `CIRCLE_SIDE` (default `right`) is the actual CSS property name, not just a value — same pattern as `4-vertical-split.html`'s `CIRCLE_SIDE`/`LOGO_SIDE`. Set `CIRCLE_SIDE: "left"` to mirror the whole inset to the opposite corner at the same size/vertical position. This is one template file serving both, not two — the wizard's "Spotlight" and "Spotlight Left" Styles are the same `11-single-circle.html` with this one placeholder flipped.

**#7 is the odd one out — no photo, ever.** Use it for a brand-manifesto/bold-statement carousel where the line itself is the visual, not a support for a photo. Don't try to force a photo into it; if the topic needs a photo to land, pick a different template instead.

**Rule of thumb:** if a slide is making an explicit "here's a real before/after" claim, it needs user-supplied photos — never substitute a stock photo into a circle badge labeled "Before"/"After," that's a false claim regardless of what project this is for. If no real photos exist for this project yet, default to templates 2, 4 (no circle), 5 (no circle), or 6 — all four work fully with illustrative/stock imagery with no proof-of-person claim attached.

**Circles 1 and 3 have no tag markup at all (removed 2026-07-20, per Jaylen).** `1-cover-circles.html` and `3-flip.html` originally had a `.tag` pill per circle — both were cut, no replacement, no `CIRCLE_L_TAG`/`CIRCLE_R_TAG`/`CIRCLE_TAG` placeholders left in either file. Only templates 4 and 5 still carry an optional tag, via the `CIRCLE_BLOCK` snippet described just below — **never default that tag's text to "Before"/"After"** if it's used: build the real label into `CIRCLE_BLOCK` explicitly, or omit `CIRCLE_BLOCK` entirely rather than reaching for a placeholder tag to suppress it.

**Templates 4 and 5's circle is a single `{{CIRCLE_BLOCK}}` placeholder, not static markup — never hand-edit generated HTML to remove it.** When a circle isn't needed, just leave `CIRCLE_BLOCK` unset in `values.json` (it defaults to empty) instead of filling the template and then deleting the circle div out of the raw HTML afterward. That manual-surgery approach is exactly how a broken regex once left an orphaned `<span class="tag">Before</span>` behind — the wrapping div got removed but the tag inside it didn't, because a naive non-greedy match stopped at the first nested `</div>` instead of the outer one. When a circle IS wanted on templates 4/5, build the full snippet as the `CIRCLE_BLOCK` value with the real image and tag baked in, e.g.:
```json
"CIRCLE_BLOCK": "<div class=\"circle-wrap\"><div class=\"circle\"><img src=\"photo.jpg\" alt=\"\"></div><span class=\"tag\">Real Label</span></div>"
```

**#5's photo strip was widened after three real complaints (twice in SwipeMaxx, twice here counting a repeat).** It was originally ~25% of canvas height and photos read as barely-there or got cropped to something unrecognizable. Strip height is now **36vh (~486px at the 1350 reference)** — still clearly text-dominant (64/36 split, this is a "stat takeover" template, not a photo template), but a real photo has actual room now. This is a floor, not a guarantee: **still render an actual test slide and look at the real output before finalizing `STRIP_POSITION`** — picking coordinates by guessing and shipping without a visual check is exactly what caused all three failures, and a wider strip doesn't make bad `STRIP_POSITION` coordinates good. Before using #5 at all, ask whether the photo's job on this slide is "recognizable subject" or "ambient texture" — it's still the better fit for the latter. If a template with a stat-driven cover matters more than the photo-strip aesthetic, #4's `.stat`/`.statlbl` cover-slide treatment gives the same "big number" effect with a full-height photo column instead of a strip at all.

**Font is parameterized but defaults to the original system font, unchanged.** Every template's `html,body` rule is `font-family:{{FONT_FAMILY|'Segoe UI', Arial, sans-serif}}`, and every `<head>` has an empty-by-default `{{FONT_LINK_HTML|}}` slot right after the charset meta tag. Leave both unset and a carousel renders exactly as it always has (every carousel made so far never set these, so nothing retroactively changes). To use a different font: set `FONT_FAMILY` to the real CSS font-stack (e.g. `'Poppins', sans-serif`) **and** set `FONT_LINK_HTML` to a real Google Fonts `<link>` tag for that family — setting only `FONT_FAMILY` without also loading the font will silently fall back to the system default, since the browser can't render a font it never downloaded. Template 2's cover caption keeps its own separate `'Impact','Arial Narrow'` treatment regardless of `FONT_FAMILY` — that's a deliberate stylistic choice for that one caption, not an oversight.

## Filling a template

1. Copy the template file to a working `slide-0N.html`.
2. Build a `values.json` with every `{{PLACEHOLDER}}` the template needs (open the file, they're easy to spot) plus `CANVAS_H` for the target format.
3. Run `python scripts/fill_template.py <template> <values.json> <output.html>`.
4. Repeat for all 5 slides (4 content + `cta.html`), then render (see SKILL.md's rendering steps).

## Caption color convention

Every caption is 2-3 `<span>` clauses: `.c1`/`.c2`/`.c3` (or `.accent`/`.muted` in the magazine/story templates) cycling secondary-accent → white → primary-accent. Cover slides render in ALL CAPS; inner slides render in normal sentence case. Don't use more than 3 clauses — it stops reading as a color *progression* and starts looking noisy.

## Color contrast against the dark background — check it, don't eyeball it

Every template's base background is near-black (`background:#0a0a0a`), and the scrim-style templates (3, 6, 9's split zone, 10) fade to that same near-black exactly where captions sit. A brand's real PRIMARY/SECONDARY color can look perfectly fine as a UI color on a white page (buttons, logos, links) and still be nearly illegible as caption/stat text on these templates — those are two different backgrounds, and "it's our brand color" doesn't mean it's readable here. This bit a real carousel: Caroslide's own brand purple, `#512888`, is dark enough that it read as invisible-ish both as plain caption text (`8-photo-grid.html`) and as an overlay caption on a photo scrim (`10-split-overlay.html`) — the failure showed up in two unrelated slides because it's the same root cause (a dark color on a dark background), not two coincidental glitches.

**The check, before finalizing any color into `values.json`:** compute perceived luminance for the candidate text color — `(0.299×R + 0.587×G + 0.114×B) / 255`, using 0-255 RGB values, giving a result from 0 (black) to 1 (white). If it comes out below roughly **0.35-0.4**, that color will read as poor-to-illegible against `#0a0a0a` and must not be used directly for `.c1`/`.c2`/`.c3` caption spans, `.stat`, or `.tagline`. For reference: `#512888` computes to ≈0.25 (fails); `#38BDF8` computes to ≈0.62 (passes comfortably); the existing default accent `#D97757` computes to ≈0.55 (passes).

**The fix when a brand's real color fails the check:** lighten it (mix toward white) until it clears the threshold — keep the hue, don't swap to an unrelated color. Worked example: Caroslide's `#512888` (fails, ≈0.25) → `#A855F7` (same purple family, ≈0.5, passes) — used as the text-safe substitute anywhere that color needs to sit on the template's dark background. The original dark hex is still fine to use where it's *not* sitting on a dark background — e.g. it worked fine as-is for a logo wordmark rendered at large weight/size directly on `#0a0a0a` in testing, so "fails the caption threshold" isn't an automatic ban on the color everywhere, just as body/caption text at normal sizes.

This check runs for every brand's colors on every carousel, not just when a color looks subjectively dark — a color that reads fine to the eye in a hex-picker swatch can still fail once it's actual text on `#0a0a0a`.

**Real finding (2026-07-21): the threshold alone isn't sufficient for photo-scrim templates.** A muted sage green, `#5B7A5E`, computes to ≈0.43 — comfortably above the 0.35-0.4 cutoff, meaning it should "pass" by this formula — and it still read as hard to see in a real render on `1-cover-circles.html`. The formula assumes a pure `#0a0a0a` background, but the scrim templates (1, 6, 9's split zone, 10, 11) aren't actually pure black where captions sit — the gradient is only 85-97% opaque, so real photo color bleeds through underneath it, which can push an already-borderline color (0.4-0.5 range) below what's actually legible. **The real fix, added the same day:** every caption/headline/kicker/story span on every photo-scrim template now has a real `text-shadow` (`0 2px 6px rgba(0,0,0,0.55)` or similar) as a deterministic backstop — this doesn't depend on getting the luminance math exactly right for every possible brand color, unlike the threshold check alone. The luminance check is still the first-pass filter (an obviously-failing color like `#512888` should never be picked at all), but don't treat a borderline pass (0.4-0.5) as fully safe without the shadow doing real work underneath it.

## Caption length discipline

This is **strategy-dependent, not a flat rule** — which content strategy (see content-strategies.md) a carousel uses decides how tight the caption needs to be.

**Value post → max 15 words per slide, 8-12 is the sweet spot.** Every slide stands alone, so one idea per slide — if it needs a comma to hold two thoughts, that's two slides, not one. This applies on top of the color-clause convention above, not instead of it: split across `.c1`/`.c2`/`.c3` clauses, don't pad a single idea out with extra words to fill three clauses. A slide should read fully in the time someone's thumb is mid-swipe — if it takes a second re-read to parse, it's too dense.

**Narrative/growth → no fixed cap.** Story/stakes slides are one connected thought building tension across a sentence or two, and forcing them under 15 words breaks the arc. A story slide running 25-35 words is normal and already proven (e.g. carousel 04's stakes slide: "Dozens of new 'tallow' brands have popped up overnight. Some cut it with seed oils and fillers to chase the trend cheaper and faster." — 27 words, reads fine because it's one continuous thought, not stacked ideas). The real test isn't a word count here, it's still one idea/beat per slide — a story slide should never try to cover two plot beats at once.

**Education → max 15 words per slide for the hook/payoff slides (1 and 4), a little more room on the mechanism slides (2-3) if the explanation genuinely needs it.** Slide 1's fact and slide 4's "so what" should hit as hard and fast as a value-post slide — a stat that takes two reads to parse has already lost the scroll. Slides 2-3 can run closer to narrative length (20-25 words) since a mechanism sometimes needs a full clause to explain correctly, but don't let that become an excuse to cram two separate facts into one slide — still one idea per slide, just occasionally a longer one.

When genuinely unsure which strategy a carousel is using, default to the value-post word cap — it's the safer, always-reads-clean option.

**These ranges are a target to actually hit, not just a ceiling not to exceed.** The failure mode that's bitten a real batch of carousels is writing something far *under* the range — 8 real Caroslide marquee covers all landed at 5-8 words against a 15-35 word range depending on strategy, reading like ad headlines instead of following any documented strategy at all. A cover/hook slide still needs to pick a real content strategy and hit its word count, not default to a punchy 5-8 word tagline just because it's the first slide someone sees. Compare against a proven example before shipping (e.g. RanchPad's succession-1 cover, ~25 words) if a caption feels thin — thin is a symptom, not a style choice.

**Wide-glyph stat numbers can overflow even within a "proven" character count.** Template 4's `.stat` sizing was tuned against examples like "100%" and "2.5x" — narrow glyphs (1, %, .,) that pack tighter than wide numerals/letters. "500M" (also 4 characters) still clipped off the frame at that same size, because 5/0/0/M are all wide letterforms with no narrow character to lean on. Character *count* alone isn't a reliable proxy for fit — render the actual stat string and look at it before shipping. Template 4 now exposes `{{STAT_SIZE|165px}}` for exactly this: size down per-stat (e.g. 125-130px for a wide 4-5 character stat) rather than shrinking the default for every carousel that uses the template.

**These ranges are a target to hit, not just a ceiling not to exceed.** The failure mode that's actually happened (twice, on the same batch) is writing something far *under* the range — a punchy 5-8 word ad-headline — rather than using the room the chosen strategy allows. Real example: 8 Caroslide marquee covers (`the-odyssey`, `world-cup-final`, `glitter-freckles`, `anthropic-valuation`, `hotdog-summer`, `dai-dai`, `spiderman-bnd`, `triple-album-day`, all in `caroslide-app/public/mock/`) all landed at 5-8 words against a 15-35 word range depending on strategy, reading like ad copy instead of following any documented strategy — compare against the proven RanchPad cover ("40% OF AMERICAN FARMERS ARE NOW 65 OR OLDER WHILE ONLY 9% ARE UNDER 35 — ROUGHLY FOUR FARMERS AT RETIREMENT AGE FOR EVERY ONE YOUNG FARMER COMING UP BEHIND", ~25 words) for what actually hitting the range looks like. A cover/hook slide still needs to pick a real strategy and hit its word count — it doesn't get to default to minimal ad copy just because it's slide 1.
